## 1. 背景（先读完再动手，不要凭常识猜）

这是一个 **indra-ocr 的浏览器端移植**：端侧文档识别，纯前端，文件不上传。
交付物是**一个自包含的 HTML 文件**（`indra-ocr.html`，约 170 KB），双击即可运行。

- 上游模型：https://huggingface.co/datalab-to/indra-ocr
- 推理：ONNX Runtime Web 1.22（WASM，多线程靠 SharedArrayBuffer）
- 线上：Cloudflare Worker，https://indra-web.firetable.tech

### 代码结构

```
build/core.js     推理核心，无 DOM 依赖，同一份代码既跑在 Web Worker 也能在主线程 import 作回退
build/app.js      界面、工作流、i18n、pdf.js 接入
build/shell.html  结构与样式，含 /*__CORE__*/ /*__APP__*/ 两个占位
build/build.py    三段源码合并成 ../indra-ocr.html（唯一构建步骤，无 npm）
serve.py          本地带跨源隔离头的静态服务器（仅本地开发用）
deploy/           Cloudflare Worker（worker.js 手写，html.js 自动生成）
tools/            审查用工具、样例生成器
```

### 模型契约（移植时必须严格对齐）

| 模型 | 输入 | 输出 |
|---|---|---|
| `det.onnx` | `x[1,1,H,W]` | `out[1,3,h,w]`（多边形热力图） |
| `rec.onnx` / `rec_cjk.onnx` | `x[B,1,32,W]` + `widths[B]` | `ids` / `conf` / `lengths` |
| `script.onnx` | 行特征 | `p[B]`（字形分流） |
| `order.onnx` | `feats[1,N,16]` + `mask` | `a[1,N,N2]` / `cls[1,N,10]` / `same[1,N,N2]` / `tab` |

META：`det_long_side=1024`、`rec_height=32`；词典 `{blank:0, chars:[...]}`。
字形分流阈值：`ADAPTIVE_MIN_H=9.0`、`ADAPTIVE_TARGET_H=12.0`、`ADAPTIVE_MAX_SIDE=2048`。

### 环境硬约束（违反其中任何一条，性能或正确性直接崩）

跨源隔离是**硬依赖**，少一个响应头就没有 `SharedArrayBuffer`，
onnxruntime-web 只能单线程：

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: credentialless
```

用 `credentialless` 而不是 `require-corp` 是刻意的：后者会拦掉没有 CORP 头的
跨源资源，而页面本来就要从 jsDelivr 取 wasm、从 Hugging Face 取 18 MB 权重。
**审查时不要建议改成 `require-corp`。**

外部依赖仅 3 个域名：`cdn.jsdelivr.net`（onnxruntime-web、pdfjs-dist）、
`huggingface.co`（模型权重）、`127.0.0.1`（本地开发）。
**没有任何遥测、埋点、beacon、WebSocket、第三方脚本。**

### 已知的、被测量过并接受或否决的结论（**不要重复报告**）

这几条都做过实测，不要再当成新发现：

| 话题 | 结论 | 实测 |
|---|---|---|
| 预取下一页 | 无效 | 200 页 57.9 s → 57.2 s，噪声 |
| `maxBatch` 8→16 | 无全局收益 | 有的文档变快，有的变慢 |
| 按 `minConf` 过滤低分行 | 零收益 | 一行都没滤掉 |
| 减少要识别的行数 | 不可能 | 识别占单页耗时 70–73%，改不动 |
| 文本层 vs OCR | 是两条独立通道 | 见下 |
| `toMarkdown` 把连续截图合成一段 | **有意为之** | 与官方 Python 实现保持一致，属于已知限制 |

**关于「读 PDF 文本层」开关**：它跟模型无关，走 pdf.js 从 PDF 里取内嵌文字，
零推理（3 页 143 ms vs OCR 708 ms，且文本层通道一条逐段耗时日志都没有）。
没有文本层的扫描件会自动回退 OCR（开关无效，实测两边结果完全一致）。
审查时不要把它当成"绕过模型的后门"或性能作弊。

## 2. 上线要求（这部分要单独审）

### 部署形态

Cloudflare Worker，**页面只有一个 HTML 文件**，没有后端、没有数据库、没有环境变量。
推理全在浏览器里跑，权重从 Hugging Face 直连，Worker 只负责递 HTML。

- Worker：`indra-ocr`，路由 `indra.firetable.tech/*`（zone `firetable.tech`）
- 在线地址：https://indra-ocr.firetable.workers.dev
- `/healthz` 返回 `ok`
- 边缘缓存 `s-maxage=300`，浏览器始终回源校验

### 必须满足的上线条件

1. 响应头里那两个跨源隔离头不能少（少了就退化成单线程，看起来像"部署坏了"）
2. 自包含单文件：样式与脚本内联，无同目录依赖
3. 不上传任何用户文件（这是产品的核心承诺）
4. 无凭据、无个人信息
5. 大文档（200 页）不崩、不卡死
6. 域名链路：Worker route 已挂，**但 `indra` 那条 DNS 记录还没拨成"已代理"**，
   所以 `https://indra.firetable.tech` 现在还连不上（这是唯一未完成的上线项）

### 许可（务必核对表述是否准确）

代码遵循上游 Apache 2.0；**模型权重是修改版 OpenRAIL-M**（科研、个人使用及
营收 2000 万美元以下的公司免费，对竞品有额外限制）。权重**不在仓库里**，
运行时从 Hugging Face 下载。仓库里没有分发权重，但 README 的许可段落不能被
误读成"整个东西都可自由商用"——请核对这段表述是否清楚。

### 仓库卫生

- 仓库刻意**不含 `samples/`**（里面两张截图含真人身份），生成器在 `tools/`
- `.gitignore` 覆盖了 `deploy/html.js`、`.env`、`*.pem`、`*.key`

**如果你无法运行浏览器，就明确标注"此项为静态阅读结论，未实测"，
不要伪装成实测过的数据。**

### 每条结论必须包含

1. **位置**：`文件:行号`
2. **复现步骤**：具体到能照着做
3. **证据**：实测数据 / 引用到的具体代码行 / 官方实现的对应位置
4. **严重度**：`阻断 / 高 / 中 / 低 / 建议`，并说明**判定依据**
5. **修法**：最小改动方案；如果有取舍，把取舍写清楚

### 硬性要求

- **禁止臆测**。没有证据的猜测必须标成"待验证假设"，不能写成结论
- **禁止复述第 1 节里已否决的结论**。你已经知道那些路走不通了
- **区分三件事**：
  - `真 bug` —— 会出错、有反例
  - `已接受的限制` —— 知道存在、有理由、和上游一致
  - `风格偏好` —— 能跑，只是不够好看
  把"已接受的限制"报成 bug 是这次审查最大的失败模式
- **不要提没有实测支撑的性能优化**。先给测量方法，再给结论
- **不要改文件**。除非我明确要求，否则只输出审查意见

### 审查维度（逐项过，每项都要有结论，包括"没发现问题"）

1. **正确性** —— ONNX 移植与官方 Python 实现是否逐字对齐（预处理、CTC 解码、
   阅读顺序、Markdown 生成）；边界条件（空页、超大图、旋转、透明通道）
2. **并发与状态机** —— 多引擎池、`runToken` 作废机制、换文件与重跑的竞态、
   abort 与超时；有没有"UI 显示完成但实际还在跑"或反过来的状态错位
3. **内存** —— 位图回收、canvas 后备缓冲、200 页文档的内存曲线、
   灯箱关闭后有没有把缓冲还回去
4. **安全与隐私** —— 凭据、外连域名、localStorage 内容、DOM 注入
   （注意：`textContent` vs `innerHTML`）、拖放与剪贴板处理
5. **性能** —— 先测量再建议；重点看单页 70% 耗时在识别上这件事有没有被绕过
6. **可用性与无障碍** —— 键盘可达性、焦点管理、`prefers-reduced-motion`、
   色彩对比度、触屏路径
7. **布局与响应式** —— 1440×900 / 390×844 两档，dpr 2 与 dpr 3
8. **上线与运维** —— Worker 响应头、缓存策略、域名链路、回滚方式、
   部署顺序（`build/build.py` → `deploy/build.py` → `wrangler deploy`）
9. **可维护性** —— 死代码、重复实现、注释与代码是否已经对不上
   （这个项目里有好几处注释描述的是被推翻的旧实现，请重点核对）
